# Bounded tagging and durable ingestion

Issue #11's remaining sequential provider bottleneck is removed for the built-in Claude classifier. The pipeline coalesces identical model/prompt/vocabulary/description identities before calls, reads the persistent cache serially, and schedules only uncached descriptions within the existing 200-classification run budget. At most four calls run concurrently by default, configurable through the service constructor with a hard ceiling of eight. Input stays bounded to 8,000 characters and the existing provider timeout/retry limit remains in effect.

Each call returns its own success outcome, so a failed classification cannot accidentally be cached as successful because another task finished. Provider calls have no Session reference. Cache and authoritative event/source-record writes remain serial. Legacy injected taggers with mutable last_call_succeeded remain serial for compatibility. Failed calls are not cached; deferred or failed descriptions can be retried next cycle. Successful unchanged replays require zero provider calls. A changed prompt/model still deliberately permits derived enrichment.

The pipeline commits each 100 observations instead of holding the whole cycle in one transaction. A later chunk failure preserves earlier event/source identities and their cache entries; the worker's existing failure path retains all source checkpoints for replay. Only a fully successful pipeline may acknowledge a fetch checkpoint. Dedupe/source hashes make replay idempotent, including observations from previously durable chunks.

Validation includes 37 focused regression tests. New fake-provider checks prove bounded concurrency, duplicate-description coalescing, budget bounds and failure retry. A late fourth-observation failure with two-observation chunks preserves exactly the first two events and source identities; replay inserts the remaining three without duplicate rows or new provider calls. No live provider invocation, ingest, corpus migration or deployment is included. Provider RPM limits still apply: concurrency is a cap, not a grant of provider quota. Real throughput depends on provider latency and rate limits; no fabricated production timing is claimed.
